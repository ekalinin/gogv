# Design

## Context

See proposal.md - Why. The repository has neither `AGENTS.md` nor `CLAUDE.md`, and `.gitignore` ignores only the `.claude/` directory, not these files. gopuml has both: `CLAUDE.md` is the single line `@AGENTS.md`, and its 64-line `AGENTS.md` carries its own rules inline, as it has no `CONTRIBUTING.md`. gogv has one: its sections are Clean-room rules (Allowed sources, Sources that are not allowed, AI assistants, Provenance lines), Changes and the specs, Checks, Commits and branches, Bug reports and License.

Checked in the repository before writing this design:

- `TestNoFusedMultiplyAdd` (`internal/layout/fma_test.go`) compiles the layout for the architectures that fuse `a*b+c` and fails on a fused instruction; the code writes `float64(x*x) + float64(y*y)` (`internal/layout/geom.go`).
- Trigonometry goes through `internal/fdlibm` (`fdlibm.Cos` in `internal/layout/node.go`); `math.Sqrt` is used directly.
- `internal/textmetrics/tables.go` is generated by `go generate ./internal/textmetrics` and says DO NOT EDIT.
- `echo 'digraph { a -> b }' | docker run --rm -i --platform linux/amd64 gogv-reference dot -Tplain` prints the reference's output, as `tools/refgen` and `tools/harvest` run it.
- A `make conformance` run without the harvested corpora rewrites `conformance-report.md` with only the curated corpus and the command line cases (269 cases against 565).
- Every entry of `known-differences.yaml` has `id`, `reason` and `change`; the tests of spec scenarios are named `Test...Scenarios`.
- The library's ban on processes, files and the network is already enforced by a test of `gogv_test.go`, and the commands are in the `Makefile`; neither needs restating.

## Goals / Non-Goals

**Goals:**

- Every agent session in the repository starts with the clean-room rule
- Each other rule lives in one place, `CONTRIBUTING.md`, read by people and agents alike

**Non-Goals:**

- Rules that a test or the `Makefile` already enforces or shows
- Tool-specific files beyond `CLAUDE.md` (`.cursor/rules`, `GEMINI.md`), the `.claude/` directory and OpenSpec's generated instructions

## Decisions

### D1. CLAUDE.md imports AGENTS.md

`CLAUDE.md` holds `@AGENTS.md`, so that Claude Code and the agents that read `AGENTS.md` load the same text, as in gopuml.

Alternatives: two files with the same text, which drift; a symbolic link, which some checkouts turn into a text file.

### D2. Only the clean-room rule is inline

The rule is needed in every session, and a pointer may not be followed, so `AGENTS.md` states it itself: work only from the published papers, the Graphviz documentation, the output of the `gogv-reference` image and gopuml's code; the source code of Graphviz and of its ports and bindings (Smetana, graphviz-pure, goccy/go-graphviz) is the hard limit, never opened, fetched or quoted, also when comparing. The rule leads with the sources to use, so that the forbidden code is named once, as the limit.

Alternative: a pointer to the Clean-room rules of `CONTRIBUTING.md` alone, which leaves the most important rule to whether the pointer fires.

### D3. Pointers name the situation

Every other line of `AGENTS.md` is a pointer that names when to read a section, with its anchor:

| When | Section of `CONTRIBUTING.md` |
|---|---|
| before observing Graphviz's behavior | `#allowed-sources` |
| when creating a Go file | `#provenance-lines` |
| before writing layout or output code | `#determinism` |
| when a change touches behavior that `openspec/specs` describes | `#changes-and-the-specs` |
| when writing documentation, comments or code | `#style` |
| before calling a change done | `#checks` |
| before committing or creating a branch | `#commits-and-branches` |

With the rule of D2 and a one-line description of the project, `AGENTS.md` stays at about 20 lines.

Alternative: one pointer to the whole of `CONTRIBUTING.md`, which gives no reason to read it at the moment a rule applies.

### D4. The conventions found move into CONTRIBUTING

- Allowed sources: the command that runs the reference, with the reason to prefer it to a system Graphviz (another version, and Pango).
- Determinism, a new section after Provenance lines: `float64(a*b) + c` and `TestNoFusedMultiplyAdd`; elementary functions from `internal/fdlibm`, `math.Sqrt` allowed; text widths only from the tables of `internal/textmetrics`, never from fonts on the host. The reason: byte-identical output on every platform, which CI checks.
- Checks: `conformance-report.md` committed only from a run with the harvested corpora; a known difference with its reason and the change that resolves it; every spec scenario covered by a test, as the `Test...Scenarios` tests cover the scenarios of one requirement each; a newly supported attribute or value updates `internal/attrs/supported.go` and the Status and "Not supported yet" lists of the README.

### D5. Style

A new section before Commits and branches: headers in sentence case; a spaced hyphen ` - ` where a dash is needed; minimal diffs that keep the existing names, so that a change can be reviewed and undone without touching what it does not change.

## Risks / Trade-offs

- [A renamed heading of `CONTRIBUTING.md` breaks a pointer of `AGENTS.md` silently] → the tasks check every anchor; the Style section asks that a renamed heading update its pointers in the same pull request
- [An agent does not follow a pointer] → the one rule that must hold in every session is inline (D2); the others are also caught by tests, CI or review
- [`CONTRIBUTING.md` grows] → each addition is a short rule under an existing or a new heading, and the contributor reads only the section a pointer names
